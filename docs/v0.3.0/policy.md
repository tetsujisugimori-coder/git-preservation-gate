# 中央保全・監査統合規約 v0.3.0 正式化案

**未採用・未発効。** 現行の適用版は [v0.2.0](../v0.2.0/policy.md)。承認・発効と適用範囲は [採用記録案](adoption-record.md) に従う。

## 1. 対象と適用

初回は、発効後に中央リポジトリで開始する新規審査とその規約解釈に適用する。既存案件の移行と他リポジトリへの適用は案件単位で判断する。適用版・規約コミット、対象成果物・証拠、操作、案件契約を固定する。[互換・移行手順](compatibility.md) に従い旧判定と根拠を保持する。

成果物・操作単位で分類し、同じPRの公開文書、非機密の原ZIP、機密原票を個別に扱う。必要な確認を、承認済みの保存対象と、その対象の安全や受入に関係する操作・依存関係に絞る。対象外であることだけで、対象内の受入を止めない。対象内の未保存・未検証は、実際の状態として記録する。

## 2. 分類

| 分類 | 対象と必須条件 |
| --- | --- |
| Level 1 通常保全 | 公開可能でGitから再取得できる通常のコード・文書と、固定した公開参照から再取得できるIssue・PR。GitまたはGitHubの履歴と案件別のCI・レビューを用いる。追加保存の指定がない場合は [Level 1の既定入力](../stage1b/issue14-level1-defaults.md) を使う。明示された追加保存は別操作として判定する。 |
| Level 2 重要証拠 | 非機密の重要原票、原ZIP、Git bundle等。再生成不能の原物も含む。承認済み永続先への実保存、保存版のreceipt、保存先からの直接再取得、サイズ・SHA-256、重要原物の全バイト比較、必要な形式別検査を確認する。 |
| Level 3 特別な機密保護 | 所有者が対象・範囲を明示して指定した場合、または適用規約の条件により最低Level 3が確定した場合に適用する。個別承認、実効アクセス権、保持条件、事前に固定した追加安全契約を確認する。 |

明白な秘密や法令・契約上の保護義務が判明した場合は、所有者指定に先立って該当資料の危険な公開・転送を止め、根拠のある保護義務を適用する。分類が未確定なら `UNKNOWN` と記録し、許可経路が確定するまで該当する操作の停止を維持する。機密性や保護義務が疑われる場合も、その範囲の危険な公開・転送・破壊を止める。独立した安全な作業は継続できる。氏名の記載だけで分類や公開可否を確定せず、文脈、識別可能性、公開範囲、適用される保護義務を確認する。

再生成不能性、喪失・破壊リスク、強い真正性・改ざん耐性の必要性は、分類と別に記録する。非機密の重要原物はLevel 2で扱い、対象リスクに応じて、作成限定、上書きの別承認、隔離復元とGitオブジェクト照合等を条件とする。保全条件の詳細は [承認・原物救済](authorization-and-rescue.md) と [Gate・監査契約](gates-and-audit.md) に従う。

追加の分類判断が必要な対象には、成果物と操作、所有者指定の時点・主体・範囲、機密性・保護義務の根拠と停止対象、非機密原物のリスクと個別条件、適用版・案件契約を記録する。秘密の実値、非公開の原物・保存先・承認票は公開記録に載せない。

## 3. 状態、原物検査、権限

保存、検証、独立性、受入の四状態と適用有無を別々に記録する。分類の変更や分類 `UNKNOWN` によって、該当する既知の保存・照合・必須CI等のFAILを消さず、その検査軸と依存する受入に残す。未確認・未実施は確認済みのFAILと区別する。詳細は [Gate・監査契約](gates-and-audit.md) を参照する。

重要原物の全バイト比較、ZIPのCRC・manifest等の必要な形式検査、bundleの自己完結性・隔離復元・Gitオブジェクト照合は [v0.2.0 §4](../v0.2.0/policy.md#4-原物検査と限界) を継承する。対象固定と先行保護は [v0.2.0 §1](../v0.2.0/policy.md#1-原則と対象固定) を継承する。四状態と追加安全契約は、分類に伴う置換・補足を [Gate・監査契約](gates-and-audit.md) に明示する。

規約の採用、案件への適用、操作承認、受入・マージ判断は個別に記録する。

## 4. 実運用の許可

[v0.2.0 §5の実運用必須条件](../v0.2.0/policy.md#5-実運用採用ゲート)を継承する。実運用の許可に先立ち、対象の操作について次の全条件を確認する。

1. 適用規約が正式採用されていること。
2. 対象ごとの契約・承認範囲が確定していること。
3. 実データの取得手順・期限・停止方式が定義されていること。
4. 実行主体と必要な権限が確認されていること。
5. 独立設計レビューが完了していること。
6. 対象となる実運用条件が実証されていること。

必須条件が一つでも未達なら実運用許可を発行しない。未確認（`UNKNOWN`）、未実施（`NOT_TESTED`）、既知の失敗（`FAIL`）を区別して記録する。独立レビューと承認は、対象・前提・適用範囲が同じ部分について根拠を示して再利用できる。軽微な文書修正は読み戻しで確認し、許可判断に影響する差分と依存箇所を[監査契約](gates-and-audit.md#独立再審査と証拠の再利用)に従って再審査する。

文書整備、合成試験のGate適合、限定技術受入、実運用の許可はそれぞれ判定する。規約採用や合成試作から実運用許可を発行しない。
